### Identity investigation on the owner's browser

The first DOM identity strategy expected canonical serialized message keys. The owner's visible normal conversations instead exposed opaque 20- or 32-character hexadecimal `data-id` values. Text and pre-plain-text envelopes existed, while the earlier bubble selectors were not reliable. Chat names and selected sidebar element IDs were not substituted as identity.

Owner-run, redacted, read-only Console outputs pasted in the conversation found:

- Base64 and hex decoding did not recover serialized message keys.
- No canonical conversation JID appeared in the inspected DOM attributes.
- An existing `model-storage` IndexedDB database was version 2070, with `chat` and `message` stores using key path `id`.
- Direct lookups of the four opaque DOM IDs as primary keys or through `internalId`/`rowId` did not match.
- In one complete 14,640-primary-key snapshot, each of the four DOM IDs matched exactly one serialized message-key payload, all in one conversation. Eleven unrelated keys used another grammar.

This supported an exact mapping for that observed session, not a general WhatsApp schema contract. The resolver now requires bounded, complete keyspace evidence and rejects ambiguity. It reads primary keys, not message contents, for identity. It does not guess identity from names or timestamps. See [opaque identity record](reviews/OPAQUE-IDENTITY.md); its original exact-version-opening description is historical and was superseded below.

**Important correction:** the original-hash message is a catch-all in `readMessageOriginal`. `projectOriginalMetadata` returns null for a missing/mismatched record, invalid or unsupported `filehash`, rejected size, MIME type, or filename. For example, it rejects sizes above 8 MiB and filenames containing forbidden characters. We have not isolated which condition fails in the owner's current records. Do not equate that message with proof that the hash is missing or the media cannot be downloaded. Do not speculate about a new hash encoding and ship another build without evidence.

Likewise, DOM media markers identify possible attachments. Their count is not proof of five distinct downloadable originals; nested/decorative/grouped markers and unavailable originals need investigation.

## Runtime, files, and recovery

- Launcher: `Start wa-scribe.command`; initial launch installs locked npm dependencies and Playwright Chromium. This is a Terminal/Node prototype, not a signed/notarized native Mac app. Node is not bundled.
- Persistent WhatsApp profile: `~/Library/Application Support/wa-scribe/chromium`.
- Local settings/chat registrations: `~/Library/Application Support/wa-scribe/local.json`.
- Default exports: `~/Documents/wa-scribe`, with an output-folder selector and `--output` override.
- Chat folders: `<sanitized Unicode chat name>--<16 hex identity suffix>`. The suffix derives from account/chat IDs; stored binding is validated before reuse. Names are labels, not identity. Same-named chats stay separate. Existing named folders retain their first label when a display name changes.
- A legacy hash-only folder is renamed intact after binding validation. Duplicate candidate folders, symlinks, or invalid/missing bindings are refused rather than adopted or replaced.
- Each chat has `binding.json`, optional `pending.json`, `CURRENT`, and `generations/<uuid>/`. The current generation contains `transcript.md`, `sync.json`, and saved media files. Open folder opens that generation directly.
- Shared `.staging` retains media needed for pending publication. Never delete it to clear a capture error.
- Current limits: 50 rendered messages/pass, 8 MiB/original, 128 files and 32 MiB/generation, 64 MiB staging, 100 registered chats. These are prototype choices, not measured platform limits.

The pending-pair defect was JSON property insertion order: fresh message drafts and decoded messages ordered `attachments`/`limitation` differently. Strict metadata decoding/binding/fingerprint validation and exact Markdown re-rendering remain; redundant raw JSON-string equality was removed. Publication preserves the journal's actual bytes and read-back checks. That specific failure can happen before `pending.json` is written, so retry Sync if there is no pending operation; use Recover when one exists.

The output lock is an atomic `.wa-scribe.lock` directory containing a random owner token. It has no PID/process-start identity. Normal close, Ctrl+C and SIGTERM release it; a crash/abrupt kill can leave it behind. Lock presence does not prove a live writer, and age/PID guesses do not justify deleting it. Stop all owning wa-scribe processes before removing only a stale lock. The panel's Recover action is for pending exports, not process locks. Existing Chromium profile, staged bytes, journals, and exports must survive troubleshooting.

## What we learned

1. Establish a real photo/PDF/text capture proof before expanding UI, archive logic, or packaging. A maintained browser process alone does not supply a dependable message/media interface.
2. Observed ordering is different from full-history coverage; one visible window is not a chat archive. One observed message with no attachment says nothing about older media.
3. Keep diagnostic failure stages separate: identity, record lookup, hash representation, optional metadata, control discovery, delivered download, byte verification, durable save. One catch-all causes repeated speculative fixes.
4. DOM rows are virtualized; scrolling, viewer opening, rendering and sidebar changes can invalidate context. Preserve binding checks and revalidate after asynchronous UI actions.
5. PDF preview controls can live in a sandboxed cross-origin iframe and can block the entire chat sidebar. Browser download events, frame/parent controls, focus, late arrivals and cleanup need direct evidence.
6. Public schema version numbers, display names, CSS classes, temporary URLs and installed-browser identity are not stable archive identity contracts.
7. Preserve original bytes and pending operations. Never weaken checks merely to make the saved-file counter increase, and never label a thumbnail or truncated file an original.
8. Separate pure format/storage correctness, synthetic browser behavior, and owner-operated live compatibility. Our previous completion language exceeded the latter evidence.

## Chromium, browser libraries, and Baileys

| Approach | What it changes | Main question to prove |
| --- | --- | --- |
| Current Playwright + DOM/IndexedDB | Owns the browser and automates visible UI | Can this source actually expose identity, history and original media reliably in the current WhatsApp version? |
| Browser-based library, e.g. whatsapp-web.js or WPPConnect | Retains Chromium while supplying existing chat/message/media access code, often via WhatsApp page internals | Does a maintained implementation solve these exact failures, with reproducible current-version evidence? |
| Baileys | A Node/TypeScript library implementing an unofficial WhatsApp linked-device client; pairs by QR and communicates without Chromium | What history and media does it actually receive, and how reliably can it resume on this account/device? |
| WhatsApp Export chat with media | Owner supplies official per-chat export bundles for import | Can manual snapshots meet the user's needs if automatic sync remains unreliable? |

Baileys is not a Chrome extension, a Chromium automation library, or a hosted service by definition. A local integration would keep its session credentials on the Mac. It has not been installed or tried here. Being independent of screen layout does not guarantee complete history, available old media, or future compatibility. Browser libraries and Baileys are unofficial approaches; verify maintenance, current versions, account restrictions and limitations from primary sources rather than assuming them.

The owner has not approved a migration to Baileys. Research Chromium-compatible solutions first, with Baileys as a serious comparison. Existing agent rules prohibit hidden/private endpoint discovery and unapproved dependencies; researching documented approaches is different from implementing private module access or a protocol client. Record the proposed implementation boundary and resolve applicable constraints before expanding into those methods. Do not interpret this document as permission to operate live accounts.
