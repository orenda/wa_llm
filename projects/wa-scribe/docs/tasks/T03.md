## Deliverables

1. **Reproducible setup guide, `docs/GOOGLE_SETUP.md`.** Explain enabling Drive API, OAuth consent/test-user configuration as applicable, a stable development extension ID, the Chrome-extension OAuth client bound to that ID, build configuration, and loading `dist/`. The OAuth client ID and any extension public key are public configuration; no private signing key, client secret, password, or token belongs in the repository or chat. If configuration is absent, the ordinary build must remain usable and the panel must state what setup is missing. Never ship a fabricated working client ID. Provide exact owner-operated steps; do not change a real Google Cloud project automatically.

2. **A small Chrome identity boundary and connection panel.** A user click starts `chrome.identity.getAuthToken` interactively; use the platform token cache and only the `https://www.googleapis.com/auth/drive.file` OAuth scope. Show the authenticated Drive account from authenticated API evidence before offering a probe; do not assume the Chrome profile label proves which account granted Drive access. Do not add identity scopes just to get a display label. Handle missing setup, denial, no usable identity, expired/revoked tokens, and account changes explicitly. Keep access tokens transient, out of Chrome storage, exports, errors, screenshots, and logs. No custom login/password/refresh-token store. Noninteractive restoration may inspect the cached connection but must not trigger consent or writes on startup.

3. **A separately clicked synthetic probe with bounded work.** Connect does not create files. After showing the account, a clear Run Drive test action creates a new isolated test root (visibly labeled as a wa-scribe test), records its returned Drive ID, then creates, reads, updates, and reads back fixed synthetic raw Markdown, JSON, and tiny media bytes under that root. Verify exact expected bytes and parent/file identities; never convert to Google Docs. Use fixed small size/request/time budgets and one in-flight probe; do not implement a general job engine. Verify HTTP responses and runtime JSON, not just successful fetch resolution. No list-by-name adoption, arbitrary existing folders, chat data, WhatsApp requests, or automatic probe on reconnect.

4. **Ownership and honest failure state.** Retained nonsecret probe state binds the authenticated account to the returned root and file IDs. Recheck that binding before writes and on reconnect; an account change or missing/inaccessible root pauses use of the old IDs. Do not silently create a replacement when reconnecting to a missing root. A timeout, lost response, worker restart, or cancellation during a mutation may have an unknown remote outcome: show that state, retain known owned IDs, and stop further mutations for that attempt. No automatic replay, blind create retry, success-shaped fallback, or claim that cancellation undid a write. A new explicit attempt must warn about unresolved prior artifacts and use an isolated root; do not treat it as recovery of the old attempt. T04/T08 will establish supported reconciliation/write guarantees. Leave cleanup user-operated in Drive for this ticket; never delete files by matching names.

5. **Tests and evidence.** Unit tests use injected identity/fetch boundaries only where needed; production must use real Chrome APIs and HTTP. Cover scope, absent config, denied consent, authenticated account display, successful byte round trip, non-2xx/invalid JSON, account change, missing root, double click, token expiry, and unknown mutation outcomes (including apply-then-response-lost). A classified authentication failure may invalidate the cached token and offer reconnect; do not automatically replay a mutation. Keep all ordinary unit/browser tests offline with the existing network allowlist. Document which interactions are mocked. Keep the real unpacked-extension shell tests passing, updating assertions intentionally when permissions/UI change.

Use compact direct functions and a few explicit states. Proposed owned paths: identity/probe modules, panel/background/manifest integration, focused tests, and the setup/evidence docs. Existing build configuration and manifest tests may change only as needed for public OAuth configuration and narrow identity/Drive permissions. Keep `src/model.ts`, `src/format.ts`, the accepted golden format, package dependencies/lockfile, Python project, and CI unchanged. No new framework, generic API client, retry subsystem, store abstraction, or full Drive adapter. If the probe grows too large for a reviewable change, stop at a documented buildable boundary and return for review rather than adding the next ticket.
