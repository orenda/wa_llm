## Findings

1. **P1 — validate a known instant before accepting it.** `src/format.ts:163` accepts any nonempty string when `precision` is `instant`. Starting with the golden sidecar, replace a message timestamp with `{ display: "09:41", precision: "instant", timeZone: null, instant: "yesterday" }`. Both `encodeExport` and `decodeMetadata` accept it. An offset-free `2026-10-19T09:41:00` is accepted too, although it does not identify an instant. This allows invalid or uncertain source time to become authoritative metadata. Define a compact explicit supported ISO instant grammar, require a UTC designator or numeric offset, validate calendar/time values, and reject invalid input without coercing localized text or supplying a timezone. Add positive and negative tests for both Markdown parsing and metadata decoding; document the accepted grammar.

2. **P2 — attachment equality depends on property insertion order.** `src/format.ts:399` compares attachment objects with `JSON.stringify`, but parsing reconstructs their fields in a fixed order. In the golden fixture, rebuild the saved attachment as `{ relativePath, mediaType, name, state }`, keeping every value unchanged. `encodeExport` returns `fingerprint-mismatch`; the original property order succeeds. The same problem applies to slot objects whose `attachment` field precedes `slot`. Valid producers should not need a JavaScript property-order contract. Compare attachment/slot values structurally and serialize them canonically. Preserve array/slot order. Add regression cases for reordered object fields and verify successful encode, decode, parse, and alignment, with stable rendered bytes.

Both findings were reproduced against the production codec using copies outside the checkout; no source or test files were changed during verification.
