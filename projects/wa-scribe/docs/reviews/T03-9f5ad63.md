## Remaining findings

1. **P1 — a probe can write to a different account than the panel displayed at the click.** `src/panel.ts:42` drops a pending Connect reply when a probe notification at `:58–60` changes its epoch; `src/chrome-drive.ts:119` dispatches probes using the worker's current global session, without binding the request to the account that its panel showed. Reproduction: panel 1 begins interactive Connect to B; panel 2's probe has already captured A's token and finishes while the B account lookup is pending. Its notification shows A and re-enables panel 1. The later Connect result is ignored by panel 1, although the worker remembers B. Clicking Run then creates a folder under B while the panel still shows A. The reviewer reproduced this through the actual panel and worker modules with fake Chrome/fetch; it is not a real Google operation. Preserve authoritative connection results across unrelated notifications, and enforce the clicked panel's expected account before any mutation. If it differs from the freshly authenticated account, display the changed account and stop before writing; require a subsequent explicit action. Add the interleaved Connect/probe/notification regression and assert zero writes to an account not shown at the click. An equivalent synchronization design is acceptable if it also covers stale multiple-panel account displays.

2. **P2 — acknowledgment identifies known files, rather than the current unresolved attempt.** `src/drive.ts:129–132`, checked at `:355–357`, derives its key solely from account/root/file IDs. Capture key K for an old pending operation; acknowledge K and let a new folder POST return 504 or lose its response before returning its new ID. The stored IDs and key are still K. A stale request acknowledging the earlier K then sends another fresh folder POST instead of returning the newer warning first. The reviewer reproduced two fresh-folder POSTs using the same historical acknowledgment. Keep a small durable mutation/attempt revision and bind acknowledgment to that revision; known IDs alone cannot identify an operation whose new ID was never received. Preserve the older revision/state when a new attempt is definitively rejected. Test: acknowledge old uncertainty → fresh create becomes unknown → old acknowledgment must stop before any HTTP; only the newly displayed state may permit a subsequent explicit attempt. No generic transaction framework is needed.

3. **P2 — exceptional probe completion does not release reopened Busy panels.** `src/chrome-drive.ts:119–127` broadcasts normal results, but returns catch results without notifying other panels. Busy polling in `src/panel-state.ts:34–45` stops after eight 300 ms refreshes. Reproduction using the actual `handleDrive` and `panel.ts` modules: block the post-create storage write, reopen a second panel, let its Busy polling budget expire, then reject that storage write. The initiating call returns `unknown-mutation`, durable pending state remains, but notification count is zero and the reopened panel stays Busy with both buttons disabled. Finish both ordinary and caught outcomes through the same state/notification path, preserving the cause classification and unknown outcome. Add a regression through the production wiring; manually passing a finished result to `planPanel` does not cover delivery. Provide a usable read-only refresh fallback when the poll budget expires and no completion arrives, including worker loss. Refresh must never trigger consent or a test automatically.
